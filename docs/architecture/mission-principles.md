## Mission-safety enforcement plan: the eight architecture principles

The mission framework applies the repository's eight principles to the user's mission-safety rules as follows:

1. **Content is data.** Story and contract definitions stay under `src/data/missions/`; the runner only interprets generic step/action kinds. The content tests resolve referenced ids and check step reachability. Each player-facing `objective` is authored separately from implementation-only `log` text, so spoiler-safe guidance is a data review rule rather than a string hidden in UI code. The limit is that validation can prove references and reachability, but it cannot prove that a writer's hint is narratively spoiler-safe; authored text still needs review.
2. **The simulation is pure.** Dialogue, inventory hand-offs, waits, flags, branches and world actions enter through mission events and emit mission/effect events; the runner does not import the DOM, renderer or keyboard. UI buttons only request dialogue progression. The current legacy runner still reads the shared plain `state` and event bus, so it is screen-independent but not yet a fully injected/server-isolated simulation; that boundary is the remaining limitation of this principle.
3. **Entities are plain data with ids; meshes are views.** Mission waves tag enemies, shots and loot with the mission id. Abandonment removes only those records through the simulation cleanup path, leaving ordinary encounters intact; render cleanup follows the entity-removal events. A mission never owns a mesh, so interruption and cleanup cannot strand a visual-only reward or hostile.
4. **All randomness goes through `util/rng.js`.** Mission data supplies ids and spawn ranges; the generic AI/spawn adapter performs any placement or behaviour rolls through the shared RNG. The mission runner itself has no random branch, which keeps retries after save/load or a blocked resource deterministic at the mission-state level. A future adapter that bypasses the RNG would violate the repository rule and is not something mission data can prevent by itself.
5. **Profile, world and session state stay apart.** Progress, flags, counters and held rewards are in the portable profile; per-place signal state is in saved world state; live mission-owned enemies, shots and crates are session entities. v19 sanitization preserves pending steps and item-blocked state. Reward hand-ins check the complete requirement before consuming stock, and script batches preflight their combined item capacity; a blocked transfer remains claimable instead of deleting the mission or item.
6. **Players are a list.** Every gameplay event carries the acting `player` and its profile. Spawn, dialogue and reward guards inspect that pilot's docked/flying/warping/dead/place state, and mission-owned cleanup is keyed by mission id. This works for the current multi-pilot simulation; the limitation is that the mission dialogue panel is still a local-player screen until the planned multiplayer presentation layer exists.
7. **Input is a command, not a key.** The mission layer receives semantic events such as `dialogue-next`, `dialogue-choice`, `place-entered`, `enemy-killed`, `docked` and `mission-inventory-changed`. A click cannot spawn a wave, move an object or start combat: dialogue transitions are marked as dialogue-only and the runner refuses to auto-run the following world script until a world event arrives. Border Signal activates and spawns only after the pilot actually enters Hollow, and UI input does not bypass resource or state checks.
8. **The simulation uses a fixed time step.** Timer, survive and timeout accounting consume `mission-tick` seconds from `sim/step.js`; an interruption, warp or reload leaves the saved counters/elapsed state to resume on a later tick. Mission actions are idempotent or remain pending until their requirements are met, so event order, late arrival and retry do not duplicate rewards. The limit is that a caller outside the fixed-step loop can emit malformed events or arbitrary `dt`; the in-game path and tests use the fixed-step adapter, while payload guards reject irrelevant events.

These principles do not authorize silent authored failure: only an explicit player abandonment or a mission definition's declared, reported cause (Border Signal currently ship destruction) removes a mission. Full cargo, missing resources, wrong place, leaving dialogue open, returning late, save/load and ordinary interruption wait or resume with an actionable objective. The framework cannot infer an author's intended failure or guarantee a player can win a deliberately impossible authored mission; content validation and the per-step requirement/resource checks are the enforcement boundary.
