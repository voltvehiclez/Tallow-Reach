# src/render: what you see in 3D

Visual only. Reads `state` and the sim, never changes game rules. Visual random choices use
`cosmeticRandom` so render frame rate does not consume seeded gameplay rolls.

| File | What it does |
|---|---|
| `scene.js` | three.js renderer, lights, stars, and per-place scenery built from `PLACE_DEFS` features (station, planet). Each place gets its own group: `placeGroup(id)`, `showPlace(id)` to show one place and hide the rest, `updateScenery(dt)` for visual spin. Step 14 added **skies**: `SKIES` is a registry of builders keyed by a place's own `sky.kind` (`placeAt(id).sky`, vocabulary in `data/instances.js` `SKY_KINDS`), each returning `{ object, spins, dispose }` like a scenery model. **There is one kind: `cube`** (owner 2026-11-15). `SKIES.cube` draws a generated cube map — six `face x face` pictures (2048 px each) on the six faces of a `BoxGeometry`, `BackSide`, unlit, no depth write, no mipmaps and one linear filter — with `shards` broken rocks drifting inside it in the shapes `rockShapeAt` gives a field, the rock catching a breath of that sky's own nebula `tint`. A box replaced the owner's equirectangular panoramas because a cube has no poles and the same texel density in every direction: the 4096x2048 panorama was stretched and magnified exactly where the camera looks on a 4K screen, which is what read as blur and distortion. Normal space (every ordinary pocket) is `DEFAULT_SKY` in `data/places.js`, and a template's own `sky` (`data/instances.js`) names a rift's or a wormhole's far side — all of them generated cube maps, all **inlined by the build** (`src/assets/skyboxes/`, esbuild `dataurl`), so nothing is painted at runtime and there are no external file paths. The six faces are in the OpenGL cube order (px, nx, py, ny, pz, nz); `render/cubemap.js` turns the top and bottom over, because `BoxGeometry` frames those two the other way up. The drawn starfield (`stars`, `STARFIELD`) is **switched off** because the pictures have their own stars; `showPlace` turns it on only for a place whose sky says `starfield: true` *and* the master switch is on, and `menuview.js` clones it only then, so nothing ever draws two sets of stars. `skyFor(def)` drops a sky nothing can draw (an uninstalled skybox id) so a typo costs a background and never the place. `forgetPlace(id)` removes a place's group for good and runs its sky's `dispose` — used for a destroyed instance, which never comes back (`main.js` on `instance-closed`, and on `instances-forgotten` after a load), and for a simple wormhole pocket that despawns (`wormhole-gone`). Scenery jitter uses `cosmeticRandom()` only. |
| `systemsky.js` | The **system sky layer** (2026-11-16): every ordinary pocket of a system — and a spawned wormhole pocket, which is a pocket of its system — gets the dynamic layer: the star/black hole hanging in its true direction from that pocket, every planet hanging as a true-angular-size body (a moderated sphere aligned with the POI/arrival horizon inside a planet pocket, a disc elsewhere; solid class colours, day/night directional shading and an additive limb), belt pockets as ochre dots, and every other pocket as a barely-visible dot. All of it derives from `systemSpatialLayout` (AUs, height 0); the body is a real 3D sphere at the sky's depth with an additive halo, its apparent size being its set AU size over the flying pocket's distance (closer pocket → bigger body; compact system → bigger sun). The layer rides inside the sky group, so it follows the camera and can never be flown to. Instances get nothing and keep their own skies. `showPlace` also re-aims the scene's one DirectionalLight from the same body (`systemLightFor`; black hole = dimmer + slight orange); off the systems the old default returns. The math is tested in `tests/system-spatial.test.mjs`. |
| `skyboxes.js` | The six faces of every **generated skybox**: `SKYBOX_URLS[id]` is `[px, nx, py, ny, pz, nz]` data URLs; the ids, names, face size and nebula colours are data in `data/skyboxes.js`. Both of its blocks are written by `tools/skybox/skybox.py --install` (recipe 24): never edit between the `GENERATED` markers. `SKIES.cube` in `scene.js` reads it, one picture per face of the box. |
| `cubemap.js` | The cube map's six faces and the one place three.js departs from the OpenGL cube convention: `CUBE_FACES` (`px, nx, py, ny, pz, nz`, also `BoxGeometry`'s group order) and `CUBE_FACE_FLIP`, with `orientFace(texture, i)` turning a face over when its frame needs it. `BoxGeometry` frames +X, -X, +Z and -Z exactly the way the generator paints them and frames +Y and -Y the other way up, so those two are flipped at load — no rotation, no mirroring, nothing per sky. `tests/skybox.test.mjs` reads `FACE_AXES` out of the generator and rebuilds `BoxGeometry`'s frames with three.js, so a wrong table fails the suite instead of showing as an upside-down patch of sky. |
| `sky.js` | The original **painter** for a sky, on a canvas (`SKY_SIZE`). Since 2026-11-14 it is **unused at runtime** — both skies are the owner's panoramas wrapped by `scene.js` directly — and it survives only for `tests/sky.test.mjs` (delete it and that suite on the owner's word). It was It replaced a shell of flat panels, which read as triangles rather than as space (owner bug report 2026-11-14), and its second round replaced painted fractures and filaments, which read as odd lines over an otherwise good sky (owner, round three). Four pure generators — `skyVeils` (enormous faint washes over the whole sphere: the nebula's body), `skyClouds` (soft roundels of the place's own light along one band, a third of them dust that eats it), `skyCores` (small bright knots: the hearts a nebula piles its light into) and `skyGrain` (six thousand single pixels under 0.04 alpha, an invisible dither that keeps dark gradients from banding into contour lines) — each take a roll function, so a test can check the sky that will be painted without a canvas; `paintSky(sky, canvas)` lays them down as gradients only, in the palette from the place's own `sky` data (`col`, `glow`, `veil`), and darkens the pinched poles. The painter **strokes nothing and starts no path**: there are no stars in any of it and no lines of any kind (owner 2026-11-14, twice), and the "shattered" half of the look is the broken rock drifting inside the shell (`scene.js`), which also gives the texture no mipmaps, so no seam can draw a line of its own. Clouds are wrapped at ±one canvas width so nothing is cut by the seam. Every number here is a look, never a rule. |
| `planetmaps.js` | Procedural **planet maps**: `planetTexture(planet)` paints an equirectangular canvas once per `planet.classId`/`planet.seed` and caches it — banded gas giants with storm ovals, ice worlds with stress lines and pale continents, mottled volcanic cracks with glowing lava cores, and cratered rocky worlds. Currently unused: owner requested solid-colour planets until a higher-quality generator exists; a future data table can swap in hand-authored maps without touching the call sites (`render/systemsky.js`, `render/models.js`). |
| `models.js` | Ship and asteroid meshes. `mkShip`, `buildPlayerShip(id)`, `fitShipModel` applies optional hull-data visual yaw/length and centres imported hulls without changing flight scale; `rockShapeAt(k)` (`ROCK_SHAPES` shapes; a rock's record says which: `shape`); built from the same positions `sim/colliders.js` uses for rock hulls. Every builder first checks for a `.glb` (see `gltf.js`) and falls back to the built-in mesh. `stationModel(f)` now draws four built-in silhouettes selected by the feature's `style` (`commerce` spun ring, `industrial` foundry stack, `military` octagonal citadel, `mining` excavation platform), each class-lit and class-accented, with `station.<class>.glb` (then `station.glb`) as overrides. `planetModel(f)` wears the procedural `planetmaps.js` texture when the feature carries a `planet` record (Lambert-lit, emissive for volcanic worlds). |
| `gltf.js` | The `.glb` registry: `preloadAfterPaint()` schedules background loading after the title can paint; Open World waits for completion. `preloadModels()` loads whatever `model-manifest.js` lists (never throws — a broken file logs and falls back), `instantiateModel(key)` clones a loaded template; compressed GLBs use DRACOLoader with the offline JS decoder in `assets/decoders/` (workers disposed after preload), `spinNodes`/`engNodes`/`namedNodes` find authoring conventions, `loadedModelKeys`/`failedModelKeys` for diagnostics. |
| `collideModel.js` | `colliderFromObject(root, { id, damage })` bakes world-space triangles of a built model into a `world-soup` collider (nodes named `noclip…` are skipped). Scenery registers these at build (`scene.js`) so the collider is exactly the drawn mesh. |
| `model-manifest.js` | AUTO-GENERATED by `build.mjs`: maps each `src/assets/models/*.glb` to its bundled (data URL) source. Includes the owner-supplied Test Ship; regenerated every build. Drop a file in, rebuild, done. |
| `views.js` | **Every mesh in the world except the scenery.** One mesh per entity, kept in step with the sim's plain data: `installEnemyViews()` at boot, `updateEnemyViews()` once a frame. Since step 7a a hostile is data (`enemy-spawned` / `enemy-removed`); since 7b so is everything else — bullets, missiles, crates, explosion sparks, rocks, and the player's own ship (built from `profile.ship`, hidden while docked). `PlayerShipView` owns the local player hull, selected by `localPlayer()`, and exposes the same named mount data the sim uses. It also draws the mining beam from `state.flight.beamStart` / `beamEnd`. `registerEntityView(kind, { list, build, update, remove })` registers a kind; one live-view map holds all kinds, with separate enemy/entity ID namespaces. `entityViewCount()` and `enemyViewCount()` count the respective views. Step 14 added three more kinds: `rift` (a door hanging in a pocket) and `gate` (the way out inside a run) — both one kind of object whose record picks the look: the **anomaly** (a door belonging to a rift: a dark spherical core with a bright eye, an additive aura and a wider flare, breathing from `performance.now()` with a per-entity phase, plus sealed shells while locked) or, since slice 14c, the **simple wormhole** (a grey dark sphere — the way in to a spawned pocket and the **Stable wormhole** way out of a natural site — cool grey core with slow-breathing grey aura and flare, no eye and no sealed state, drawn by `buildSimpleWormhole`/`updateSimpleWormhole`). Both are drawn by a shared dispatcher (`buildDoor`/`updateDoor`) reading `e.variant` on the record — never the template. `cache` is the prize **canister** (a drum, two caps, two bands and a lamp that is red while sealed and green once open). Each is built from its record's `pos`, `quat`, `spin` and radius `r` and shares one geometry and material per kind. Builds a mesh on `entity-spawned`, removes it on `entity-removed`, and sweeps the lists every frame so nothing is ever left behind. |
| `menuview.js` | The title screen's own scene: the home station turning with its planet behind it, plus the **generated normal-space skybox** (`SKIES[kind]` from `scene.js`, the authored home pocket's sky or `DEFAULT_SKY`), on the camera path in `MENU_CAMERA`/`menuPose` (`data/camera.js`). The planet is a fixed class world made in-scene (`makePlanet("menu-backdrop", …)`), not a place feature — planets are warpable pockets now. Independent of the game scene, so the menu never shows the last game view. `updateMenuView(dt)`, `menuView()`, `resizeMenuView()`; driven by `main.js` only. |
| `camera.js` | Docked orbit, chase camera, free orbit (Alt), screen shake, the FOV/roll kick during a warp. The Wasp chase distance is the `CAMERA` table in `data/camera.js`; every other ship scales both distance and height by its actual fitted model bounding diagonal relative to Wasp (`shipCameraScale` in `models.js`, cached), with optional per-hull `cameraPadding` (Test Ship: 1.2). Free-orbit distance/zoom limits use the same ratio, and Wasp stays exactly unchanged: the camera rides along with the ship's movement and only eases the offset. The free orbit looks at the ship with the **ship's** up vector (`faceUp` in `util/math.js`), so roll (E/Q) rolls the view with the hull — the mouse orbits and the wheel zooms, and nothing else does while Alt is held. |
| `warpfx.js` | The warp streaks: additive lines hanging off the camera, driven by `state.warp.fx`. Hidden when no warp is running. |
| `target-picking.js` | Exact visible-surface reticle raycast for all lockable meshes, including station children and animated parts; returns only a plain target reference to the sim. Faint glow/aura geometry is ignored. |
| `shipviewer.js` | The Outfitting ship view: its own renderer, scene, lights and turntable. `setShip(id)`, `dragShip`, `zoomShip`, `resizeShipViewer`, `renderShip(dt)`. Owned by `ui/outfitting.js`. |

Rules:
- three.js is bundled by `npm run build`. Do not add other libraries.
- A new ship needs no change here unless it has a visible add-on (`buildPlayerShip`).
- **A new entity kind is drawn here, never in `sim/`.** Give it a `kind` in its record and register its list, mesh builder, per-frame updater and
  cleanup in `views.js` (see recipe 19 in `docs/HOW_TO_ADD.md`); `tests/layers.test.mjs` fails if a `sim/` file's code names a mesh, a material
  or the scene, and `tests/views.test.mjs` counts the meshes.

The current player hull and beam views follow the **local** player only; see the still-local-only table in `docs/TARGET_ARCHITECTURE.md`.


Outfitting preview/reset uses data/camera.js SHIP_PREVIEW: front/top/left isometric yaw/pitch. Drag and zoom remain unchanged; automatic rotation is removed, with the approved initial angle preserved.

Flight scene has one faint nebula AmbientLight, updated on showPlace from data/lighting.js. Sky tint defaults to generator metadata, not pixel sampling. Existing sun, hemisphere light, title and outfitting lights are unchanged.

views.js also exports interpolatedVelocity for HUD ballistic prediction at the same frame alpha as interpolatedPos/renderPlayerPose. Missing history or teleport jumps use current velocity.
