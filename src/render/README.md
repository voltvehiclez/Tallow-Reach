# src/render: what you see in 3D

Visual only. Reads `state` and the sim, never changes game rules. Visual random choices use
`cosmeticRandom` so render frame rate does not consume seeded gameplay rolls.

| File | What it does |
|---|---|
| `scene.js` | three.js renderer, lights, stars, and per-place scenery built from `PLACE_DEFS` features (station, planet). Each place gets its own group: `placeGroup(id)`, `showPlace(id)` to show one place and hide the rest, `updateScenery(dt)` for visual spin. Step 14 added **skies**: `SKIES` is a registry of builders keyed by a place's own `sky.kind` (`placeAt(id).sky`, vocabulary in `data/instances.js` `SKY_KINDS`), each returning `{ object, spins, dispose }` like a scenery model; `SKIES.shattered` wraps **the owner's own panoramas** (2026-11-14) around the inside of a sphere — unlit and seen from the back, so no facet ever shows — with drifting rock debris inside it, in the same shapes `rockShapeAt` gives a field; a template's `sky.variant` picks the ordinary rift's teal maelstrom or the deep rift's near-black sky (`"deep"`). Slice 14c added `SKIES.shroud`, the far side of a simple wormhole: the owner's dark-grey nebula panorama with few stars (2026-11-14), wrapped the same way. Both are equirectangular images (a sphere's UV unwrap is exactly that projection) **inlined by the build** (`src/assets/`, esbuild `dataurl`) — nothing painted at runtime and no external file paths. The pocket a wormhole hangs in declares no sky at all — it is ordinary space in the system it spawned in and hangs the same starfield as every sibling pocket. A place with a sky hides the ordinary starfield (`showPlace`) and carries its sky with the camera (`updateScenery`). `forgetPlace(id)` removes a place's group for good and runs its sky's `dispose` — used for a destroyed instance, which never comes back (`main.js` on `instance-closed`, and on `instances-forgotten` after a load), and for a simple wormhole pocket that despawns (`wormhole-gone`). Scenery jitter uses `cosmeticRandom()` only. |
| `sky.js` | The original **painter** for a sky, on a canvas (`SKY_SIZE`). Since 2026-11-14 it is **unused at runtime** — both skies are the owner's panoramas wrapped by `scene.js` directly — and it survives only for `tests/sky.test.mjs` (delete it and that suite on the owner's word). It was It replaced a shell of flat panels, which read as triangles rather than as space (owner bug report 2026-11-14), and its second round replaced painted fractures and filaments, which read as odd lines over an otherwise good sky (owner, round three). Four pure generators — `skyVeils` (enormous faint washes over the whole sphere: the nebula's body), `skyClouds` (soft roundels of the place's own light along one band, a third of them dust that eats it), `skyCores` (small bright knots: the hearts a nebula piles its light into) and `skyGrain` (six thousand single pixels under 0.04 alpha, an invisible dither that keeps dark gradients from banding into contour lines) — each take a roll function, so a test can check the sky that will be painted without a canvas; `paintSky(sky, canvas)` lays them down as gradients only, in the palette from the place's own `sky` data (`col`, `glow`, `veil`), and darkens the pinched poles. The painter **strokes nothing and starts no path**: there are no stars in any of it and no lines of any kind (owner 2026-11-14, twice), and the "shattered" half of the look is the broken rock drifting inside the shell (`scene.js`), which also gives the texture no mipmaps, so no seam can draw a line of its own. Clouds are wrapped at ±one canvas width so nothing is cut by the seam. Every number here is a look, never a rule. |
| `models.js` | Ship and asteroid meshes. `mkShip`, `buildPlayerShip(id)`, `rockShapeAt(k)` (`ROCK_SHAPES` shapes; a rock's record says which: `shape`); built from the same positions `sim/colliders.js` uses for rock hulls. Every builder first checks for a `.glb` (see `gltf.js`) and falls back to the built-in mesh. |
| `gltf.js` | The `.glb` registry: `preloadModels()` loads whatever `model-manifest.js` lists (never throws — a broken file logs and falls back), `instantiateModel(key)` clones a loaded template, `spinNodes`/`engNodes`/`namedNodes` find authoring conventions, `loadedModelKeys`/`failedModelKeys` for diagnostics. |
| `collideModel.js` | `colliderFromObject(root, { id, damage })` bakes world-space triangles of a built model into a `world-soup` collider (nodes named `noclip…` are skipped). Scenery registers these at build (`scene.js`) so the collider is exactly the drawn mesh. |
| `model-manifest.js` | AUTO-GENERATED by `build.mjs`: maps each `src/assets/models/*.glb` to its bundled (data URL) source. Empty in the repo; regenerated every build. Drop a file in, rebuild, done. |
| `views.js` | **Every mesh in the world except the scenery.** One mesh per entity, kept in step with the sim's plain data: `installEnemyViews()` at boot, `updateEnemyViews()` once a frame. Since step 7a a hostile is data (`enemy-spawned` / `enemy-removed`); since 7b so is everything else — bullets, missiles, crates, explosion sparks, rocks, and the player's own ship (built from `profile.ship`, hidden while docked). `PlayerShipView` owns the local player hull, selected by `localPlayer()`, and exposes the same named mount data the sim uses. It also draws the mining beam from `state.flight.beamStart` / `beamEnd`. `registerEntityView(kind, { list, build, update, remove })` registers a kind; one live-view map holds all kinds, with separate enemy/entity ID namespaces. `entityViewCount()` and `enemyViewCount()` count the respective views. Step 14 added three more kinds: `rift` (a door hanging in a pocket) and `gate` (the way out inside a run) — both one kind of object whose record picks the look: the **anomaly** (a door belonging to a rift: a dark spherical core with a bright eye, an additive aura and a wider flare, breathing from `performance.now()` with a per-entity phase, plus sealed shells while locked) or, since slice 14c, the **simple wormhole** (a grey dark sphere — the way in to a spawned pocket and the **Stable wormhole** way out of a natural site — cool grey core with slow-breathing grey aura and flare, no eye and no sealed state, drawn by `buildSimpleWormhole`/`updateSimpleWormhole`). Both are drawn by a shared dispatcher (`buildDoor`/`updateDoor`) reading `e.variant` on the record — never the template. `cache` is the prize **canister** (a drum, two caps, two bands and a lamp that is red while sealed and green once open). Each is built from its record's `pos`, `quat`, `spin` and radius `r` and shares one geometry and material per kind. Builds a mesh on `entity-spawned`, removes it on `entity-removed`, and sweeps the lists every frame so nothing is ever left behind. |
| `menuview.js` | The title screen's own scene: the home station turning with its planet behind it, on the camera path in `MENU_CAMERA`/`menuPose` (`data/camera.js`). Independent of the game scene, so the menu never shows the last game view. `updateMenuView(dt)`, `menuView()`, `resizeMenuView()`; driven by `main.js` only. |
| `camera.js` | Docked orbit, chase camera, free orbit (Alt), screen shake, the FOV/roll kick during a warp. The chase distance behind the ship is the `CAMERA` table in `data/camera.js` and nothing else: the camera rides along with the ship's movement and only eases the offset. The free orbit looks at the ship with the **ship's** up vector (`faceUp` in `util/math.js`), so roll (E/Q) rolls the view with the hull — the mouse orbits and the wheel zooms, and nothing else does while Alt is held. |
| `warpfx.js` | The warp streaks: additive lines hanging off the camera, driven by `state.warp.fx`. Hidden when no warp is running. |
| `shipviewer.js` | The Outfitting ship view: its own renderer, scene, lights and turntable. `setShip(id)`, `dragShip`, `zoomShip`, `resizeShipViewer`, `renderShip(dt)`. Owned by `ui/outfitting.js`. |

Rules:
- three.js is bundled by `npm run build`. Do not add other libraries.
- A new ship needs no change here unless it has a visible add-on (`buildPlayerShip`).
- **A new entity kind is drawn here, never in `sim/`.** Give it a `kind` in its record and register its list, mesh builder, per-frame updater and
  cleanup in `views.js` (see recipe 19 in `docs/HOW_TO_ADD.md`); `tests/layers.test.mjs` fails if a `sim/` file's code names a mesh, a material
  or the scene, and `tests/views.test.mjs` counts the meshes.

The current player hull and beam views follow the **local** player only; see the still-local-only table in `docs/TARGET_ARCHITECTURE.md`.
