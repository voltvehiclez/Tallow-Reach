# src/data: tuning and content tables

Plain objects and numbers only. No imports from other layers (except other data files). Safe to edit for balance.

| File | What it holds |
|---|---|
| `scenery.js` | `BELT_LABEL_GAP_METRES` controls HUD grouping only. Planet backdrop size/elevation and seeded belt irregularity/stray tuning. |
| `lighting.js` | Subtle nebula ambient fill (default intensity 0.175): automatic generated skybox tint, global/per-sky/per-place overrides and safe pure resolver. |
| `audio.js` | Scheduled mechanical undocking layers. |
| `simulation.js` | Fixed simulation tick (`SIM_DT`), maximum accepted render-frame time (`MAX_FRAME_DT`) and how often the resume point is autosaved (`AUTOSAVE_SECONDS`). |
| `multiplayer.js` | The co-op rules (step 16, slice 1): `TRAVEL_FIELDS` (the pilot-owned half a guest carries between worlds — credits, fleet, fits, holds, hull damage, missiles, selected weapon bays, and the `lockers` pseudo-field for station storage), `HOME_FIELDS` (what never travels — missions, flags, stats, campaign, home station, filter presets), `ARRIVAL_STATION`/`ARRIVAL_STATION_KEY` (Meridian, read from `places.js`), `AWAY_FIELDS`/`GUEST_FIELDS` (the save v29 marker and a host's guest record, in written order), `NET` (snapshot/heartbeat/lastSeen/offer timings, guest and name limits, token size, how many previous save versions to keep; each line names its slice) and `KEY` (the `away:<worldId>` suitcase key and the `:tmp`/`:prev` suffixes). Slice 8a adds `SHIP_FIELDS` (what a ship snapshot carries about one pilot — a picture, never game state; `shield` joined `hull` in playtest 23 so a friend's second bar is real),, `HOST_PILOT_ID` (the host's own hull on the wire) and `SHIP_STREAM` (`hz` 24 = the owner's 20–30 Hz ship snapshots, **not** the 2 s `NET.snapshotSec` suitcase sync; `delayMs` 100, `samples`, `staleMs`, `snapM`). Slice 8b adds `CONTROL_FIELDS` (what a guest is asking for — `steer`, `roll`, `thrust`, `strafe`, `lift`, `stop`, `brake`, `boost`, `fire`, `sec`, `aim`), and **`CONTROLS`** (`hz` 30 — the guest's asking, not the ship's picture; `staleMs` 400, after which a silent visitor is asked for nothing). Read by `net/custody.js`, `net/multiplayer.js`, `net/ships.js`, `net/protocol.js`, `sim/multiplayer.js`, `render/shipstream.js`, `state/profile.js` and `state/storage.js`; `tests/multiplayer-custody.test.mjs` fails if a new profile field is in neither list, and `tests/multiplayer-slice8a.test.mjs` pins `SHIP_FIELDS` against what the wire carries. |
| `mounts.js` | Named hull-local gun, missile and beam mount offsets, shared by the sim and `PlayerShipView`. |
| `ships.js` | Hulls the player can fly, multi-instance ship helpers (`shipTypeOf`, `shipDef`, `shipName`, `shipBonuses`, `nextShipId`), and the `FLIGHT` table that scales every ship at once. Baseline hulls share 1× Hull HP (`hpMul`) with unique bonuses (Wasp none, Prospector `mine: 2`, Bulwark `dmg: 1.5`, Test Ship `hpMul: 100` and `dmg: 10`); fitted modules drive speed/turn, shields and Hull HP. |
| `items.js` | `ITEMS`: the whole item catalogue — every ore, salvage good, mission object and **module**, keyed by id, with a category (`cat`), sell value (`v`), volume in m³ (`vol`), stack rule (`st`), and for ores an asteroid base surface colour (`col`, read via `rockColor(id)` with `DEFAULT_ROCK_COLOR` fallback; zero self-glow). Mission objects may set `v: 0` and are not sellable. A module's entry is `{ cat: "module", v: 540 }`: its name, volume and stats live in `modules.js` under the same id (`npm test` checks both directions), and `v` is what a spare part sells for — 60% of its shop price, never below 1 credit. Adding an item is one line; read them through `itemName`/`itemVol`/`itemValue`/`canSell`/`isModule`/`rockColor`, never by hand. |
| `weapons.js` | The missile's flight and lock-on numbers and the ammunition price (`unitPrice`). Guns, the mining beam and the missile launcher are modules (`data/modules.js`), not weapon data. |
| `shops.js` | `SHOPS`, `SHOP_GROUPS` and `MODULE_SUBCATEGORIES`: what each shop sells and how the compact Shop tree groups it (`ships`, `modules` with subgroups matching `MODULE_GROUPS` — plus `Cannons`, `Missiles` and `Mining beams` sub-categories under `Primary weapons` — `consumables`, `ores`, `loot`). Stock rows name either an item (`id` from `items.js`) or a hull (`kind: "ship"`, `id` from `ships.js`), with `price`, optional `n`/`d`, optional `max` (`N left`) and optional `own: false`. Read via `shopRow(shopId, id, kind)` and `shopGroupFor`; bought through `sim/economy.js` `buyItem(shopId, id, qty, kind)`. |
| `station.js` | Base modules, their costs, storage and refinery numbers, repair and recovery fees. |
| `contracts.js` | Compatibility re-export of the mission contract templates. New mission/contract data lives in `missions/`. |
| `campaign/` | The authored campaign order: `chapters.js` (chapters and their acts, flat `CAMPAIGN_ACTS`; acts without a `mission` are `planned` boxes, chapters 2–4 are `planned`), `index.js` (lookups and `CAMPAIGN_MISSIONS`) and one file per campaign mission (`m01.js` is the flight-school tutorial). Campaign missions are separate from the open-world `STORY_MISSIONS` list and are installed by campaign mode. |
| `flight-courses.js` | `FLIGHT_COURSES`: authored flight courses a story ship leads — a fixed start and heading per phase (`lesson`, `chase`) plus legs (`length`, `speed`, optional `turn`/`climb`, `boost`). Read by `sim/flight-course.js`; a mission names the course and phase, and "back to the beginning" is the same fixed point every time. |
| `missions/` | Mission vocabulary plus data-only contract and story definitions. Each story definition may add `offeredAt` (the one station that offers it; defaults to its hand-in station, else the home station — a mission is never offered everywhere, and an unknown id offers it nowhere), and each active mission uses `{ id, title, kind, requires, steps, rewards, handIn, fails }`; each player-facing step can provide a spoiler-safe `objective` sentence, while `log` remains compatibility/internal text. `handIn.objective` is the sentence shown after the last step while items are still owed (required by the linter for any item-bearing mission; `{count}`, `{item}` and `{station}` are filled in). 13b story steps cover dialogue/choices, scripts, waits, flags/branches and parallel objectives. The runner is in `sim/missions.js`. Files in `missions/`: `index.js` (vocabulary: kinds, step kinds, `STORY_MISSIONS`, `storyMission(id)`), `contracts.js` (today's contract types as data), `story.js` (the Border Signal story mission), `templates.js` (builders for new missions: `briefing`, `radio`, `travelTo`, `loadCargo`, `handOver`, `ambush`, `mineOre`, `sequence`, `mission`), `rules.js` (numbers the linter enforces, e.g. `minSpawnDistance`), `validate.js` (the mission linter) and `test-missions.js` (four example missions shown under "Test missions" when the game is opened with `?testmissions`). Rules: `docs/MISSION_RULES.md`. |
| `camera.js` | `CAMERA`: the chase-camera trail distances (idle, full speed, reverse). The camera feel is settled: do not change it unasked. |
| `places.js` | Systems (non-flyable groupings) and pockets (flyable places): authored `PLACES`, `PLACE_DEFS` features (station, asteroid field, spawner, planet, encounter), generated `template` ids, explicit `PLACE_LINKS`, `DEFAULT_PLACE`, `pocketsIn`/legacy `nextPocket`, and `PLACE_EXTENT`. `setPlaceCatalog` installs the resolved seed galaxy as the live lookup catalog on boot/load/import; lookups fall back safely to the starting pocket. Internal ids are save ids. |
| `galaxy.js` | Starmap tuning: `GALAXY` (seed, system count, organic layout, degree cap/depth tuning, visibility policy, advisory difficulty, free intra-system travel default with a per-system `intraSystem: "links"` opt-out, empty route cost/requirements, varied generated `stationNameStyles`, galaxy chart padding/radii/zoom, `panSpeed`/`systemEntryZoom`/`transitionMs`/popup `context`, and `systemMap` orbital radii/padding/exit length/zoom plus 5% black-hole chance, map-unit core radii and label offset/line-height/gap, the visiting-pilot blip's `pilotBlipGap` (step 16 slice 7), plus `systemSpace` — the AU scale: `auPerMapUnit` × a seeded per-system multiplier in `[minScale, maxScale]`, the star/black-hole set sizes/looks and light colours, the pocket-dot look and the sky-layer radius), `GALAXY_OVERRIDES` (move system/pocket `mapPos`, author visual-only `core`, delete/promote/route edits by stable id) and `SYSTEM_NAME_PARTS`. Resolved by `sim/galaxy.js`, installed by `sim/galaxy-session.js`, and read by the live M starmap, warp rules and the system sky layer. Pocket map and AU layouts are derived, not saved. |
| `terms.js` | Generic player-facing nouns: `TERMS.mapNode` ("system") and `TERMS.flyable` ("pocket"), each changeable in one line; `term`/`Term`/`terms` helpers. |
| `sectors.js` | Warp timing and curves only (`WARP`, `WARP_TIME`, `warpFlashAt`, `warpPhaseAt`, `WARP_COAST`). Geography lives in `places.js`. |
| `outfitting.js` | `MODULE_GROUPS` (name and description per bay group), `SHIP_LAYOUTS` (how many bays each hull has of each group), `layoutFor`/`slotsFor`, and `APPEARANCE_SLOTS` (the paint bays under the hull). |
| `encounters.js` | `ENCOUNTERS`: hostile patrols, friendly traders, derelicts and resource caches, with references and slow respawn timers. |
| `place-templates.js` | `PLACE_TEMPLATES`: reusable generated-pocket scenery and tiered encounter pools, and `varyTemplateFeatures` — the seeded per-pocket variation (field position/radius/count/height per pocket, some trade lanes and outposts lose their field entirely, two fields never share a spot). Generated gate trader features are suppressed for station-pocket detachment unless an author explicitly opts into gate co-location; `features`/`extraFeatures` are preserved as explicit additions. Static (`encounter`-kind) derelict/cache features are no longer generated; patrols/traders are `spawner` features. |
| `planets.js` | Planet classes for the generated universe: `PLANET_CLASSES` (rocky, ice, gas giant, earth (greenish-grey Earth-like; also the main-menu backdrop world), volcanic — radius ranges, palette, atmosphere, spin, rock count/size, ore table), `PLANET_CLASS_IDS`, `planetClass`, and `makePlanet(id, coreName, letter, systemId, seed)` — the deterministic record (`n` `<Core>-b` … with `b`…`e`, radius, atmosphere, colour, `spin`, `approach`, `orbit`, `rockCount`, `ore`) a generated planet pocket carries. `AU_METRES` converts the AU map layout to metres for true-angular-size rendering. Planet maps start procedural (`render/planetmaps.js`); a future data table can point at hand-authored maps. |
| `stations.js` | Station classes for the generated station families: `STATION_CLASSES` (commerce, industrial, military, mining) — name, built-in silhouette id, colours, accent, light colour and class-weighted name styles. `stationClassForId(id)` FNV-hashes a place id to a class; `stationStylesForClass(cls)` returns the name-style pool the generator draws from. Optional `station.<class>.glb` models override the built-ins; the shared `station.glb` is the final fallback. |
| `skyboxes.js` | The generated skyboxes as plain data: `SKYBOXES[id] = { n, preset, seed, face, tint }`. One line per sky between the `GENERATED` markers, written by `tools/skybox/skybox.py --install` (recipe 24), never by hand. `face` is the pixels per side of each of its six cube faces. A sky is `sky: { kind: "cube", skybox: id, shards, starfield }` — a template's, or `DEFAULT_SKY` for ordinary pockets; `starfield: true` asks for the drawn starfield on top of the picture (off: the skies have their own stars, owner 2026-11-15). `tests/skybox.test.mjs` checks that every id has its six faces, imports and recipe. |
| `instances.js` | `WORMHOLE_SYSTEMS` configures the 30 starting off-chart systems, their connection cap/odds; `WORMHOLE_ENVIRONMENT` supplies the common simple/system wormhole sky, fill and core rules. Rifts and instances (step 14). `RIFT`: how a pilot opens one and gets out — `enterRange`/`exitRange` for the close-range key press, the `warnSec` collapse warning, and the `clearance` in metres from a station, an asteroid field's edge, a planet's surface and any single rock. `INSTANCE_TEMPLATES`: one temporary, generated, harder place per entry — name/description, advisory `tier`, an optional `lifetimeSec` (left out, a run gets `RIFT.defaultLifetimeSec`, 20 minutes; 0 = no limit of its own), the `difficulty` `{hp, dmg}` scalars applied to every hostile inside, the `guardians` wave, the `objective` (its HUD sentence `n` and the `done` sentence said once when it is met), the `exit` (its name, the `pos` and drawn size `r` of the gate object it hangs, plus the `requires` that hold it shut), what running out of time does (`onExpire`), the prize `cache` (its name, loot table, `pos` and drawn size `r`; opened with **R** as a two-column trade with the pilot's hold, never spilled into it), the `enter` point, the `sky` it is seen under (`col`, `glow`, `veil`, `shards` — a dark cold nebula of gradients only, with drifting rock, **no stars and no lines**), and ordinary `features` — **never a `planet`**: a run is somewhere else, so nothing in it is copied from the space outside. `RIFTS`: which templates an item can open, as a weighted pool. Vocabulary lists `OBJECTIVE_KINDS`, `EXIT_REQUIREMENT_TYPES`, `EXPIRY_OUTCOME_TYPES` and `SKY_KINDS` say what the registries in `sim/instances.js` and `render/scene.js` may be asked for; `instanceIdFor(templateId, seed)` derives the place id, so one seed is always one instance. |
| `enemy-ai.js` | Per-type movement personalities, standard fallback, `aiTuning` overrides and flight/avoidance/aim-spread tuning, plus the NPC pilot adapter's gain/boost threshold. No weapon damage or hull buffs. |
| `enemies.js` | `ENEMIES`: every hostile, keyed by id — name (`n`), plural name (`pl`), Hull HP (`hp`), colour (`col`), scale, faction (`f`), behaviour (`ai`) and all its numbers (speeds, ranges, fire gap, damage, bullet speed, spawn distance). `DEFAULT_ENEMY` is what the spawner falls back to; `enemyDef(id)` looks one up. Adding an enemy is an entry here. |
| `loot.js` | `LOOT_TABLES`: what a kill drops (`kind: "drops"` — a line per drop with a chance `w`, a count range `c` and a scatter `j`), what a derelict leaves behind, and the ore a rock is made of (`kind: "pick"` — weighted `w`). Rolled by `sim/loot.js`; an enemy names its table with `loot`. `DEFAULT_LOOT` is the fallback. |
| `factions.js` | `FACTIONS`: who a hostile belongs to (`pirates`, and since step 14 the rift's own guardians), with a name and a description. An enemy names one with its `f` field and the id travels with the `enemy-killed` event. |
| `modules.js` | `MODULES`: every part that can sit in a bay (`g` group, `vol` m³ it takes in a hold or in storage, `n`, `d`, and the stat it feeds: `mjps`, `mj`, `spd`/`turn`, for thrusters the power appetite `draw`/`boost`/`ign` and the boost tank `bmax`/`buse`/`bfill`, for shields `sh`/`regen`/`delay`/`draw`/`drain`, and for the hull `hp`, and for primary weapons `dmg`/`rate`/`bspd`/`draw` plus `barrels` for linked multi-barrel guns). `STOCK_FIT`: what a hull is delivered with. |

Rules:
- Keep the short keys (`n` name, `d` description, `v` value, ...). Copy an existing entry when adding one.
- `npm test` (`tests/content.test.mjs`) fails if an entry is missing a field.
- Adding a ship, item or contract type: see `docs/HOW_TO_ADD.md` recipes 1 to 3.
- A module needs an entry in `items.js` as well as `modules.js` (recipe 16 step 1), and a row in
  `shops.js` if the player should be able to buy one (recipe 4).

Imported ship visuals may set `modelYaw` (radians) and `modelLength` (metres along −Z); the renderer centres and uniformly fits them without changing gameplay `sc`. **`modelYaw` corrects the SOURCE model, so a replacement .glb usually needs a different value**: some exports carry their own rotation on the node (Test Ship's `testship-v1.glb` ships +90° Y), and yaw that was right for the old file then points the ship sideways. `tests/compressed-model.test.mjs` applies the node rotation and the yaw to the nose vector and asserts it ends up at −Z, so this cannot come back unnoticed.

Optional `cameraPadding` multiplies automatic model-relative camera framing (default 1); Test Ship uses 1.2 after owner playtesting. It does not change model or flight scale.

Weapon modules may declare `weaponFamily` (cannon, mining, missile) for shared hotbar icons across variants. Existing bay counts are unchanged; hotbar exposes five positions per bank.

weapons.js exports BULLET_LIFETIME shared by projectile expiry and the ballistic intercept instrument.
